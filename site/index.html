Bash · Ubuntu 24.04 · idempotent

Set up a fresh Ubuntu VPS the same way every time, and prove the re-run changes nothing.

I kept doing the same first hour on every new server: a non-root user, a firewall, fail2ban, updates, Docker, a reverse proxy, then SSH hardening. This is that hour as one bash script you can read top to bottom. It has a dry-run mode, and a second run reports "No changes were needed".

Ubuntu 24.04 only. I have not yet run it on a real VPS: it is tested in an ubuntu:24.04 container, which cannot cover swap, UFW or a live SSH reload. Try it on a throwaway server first.

The ten steps, in run order

Each step is one file in steps/. Open one to see what it protects against and how to check it afterwards. Run ./bootstrap.sh --list to print the same order from the script itself.

1 user Day-to-day work as root, where one mistake or one stolen session owns the machine.

Creates a non-root account (deploy by default, set BOOTSTRAP_USER), adds it to sudo, and installs your public key. File: steps/05-user.sh.

Verify

id deploy
sudo ls -l /home/deploy/.ssh/authorized_keys

Expect sudo in the groups and a key file with mode -rw-------.

2 swap The kernel OOM killer stopping services when a small VPS runs out of memory.

Creates a 2 GiB swap file (SWAP_SIZE, SWAP_FILE) and adds it to /etc/fstab. It leaves existing swap alone and checks free disk first. File: steps/10-swap.sh.

Verify

swapon --show
grep swapfile /etc/fstab

Not covered by the container tests: containers skip this step, so the real creation path is untested.

3 unattended-upgrades Known vulnerabilities staying unpatched because nobody logged in to run apt upgrade.

Installs the package and enables daily updates. Automatic reboot is off on purpose: a kernel update only applies after a reboot, and when that happens is your call. File: steps/20-unattended-upgrades.sh.

Verify

cat /etc/apt/apt.conf.d/20auto-upgrades
systemctl list-timers 'apt-daily*'
4 fail2ban Password-guessing bots hammering SSH, by banning an address after repeated failures.

Installs fail2ban and writes a drop-in jail: ban for one hour after five failures in ten minutes, reading the systemd journal. The config is checked with fail2ban-client -t before the service is touched. File: steps/30-fail2ban.sh.

Verify

sudo fail2ban-client status sshd
5 log-rotation Logs filling the disk until the server stops working.

Installs logrotate and caps the systemd journal at 500 MB and one month. Ubuntu already rotates files in /var/log. File: steps/40-log-rotation.sh.

Verify

cat /etc/systemd/journald.conf.d/50-server-bootstrap.conf
journalctl --disk-usage
logrotate --debug /etc/logrotate.conf
6 ufw Unexpected inbound services being reachable from the internet.

Default-deny inbound, then allows SSH, 80 and 443, then enables the firewall. SSH is allowed before the firewall turns on. File: steps/50-ufw.sh.

Verify

sudo ufw status verbose

Expect Status: active and default deny (incoming). Not covered by the container tests: containers skip this step.

7 docker Workloads running without isolation, and unbounded container logs filling the disk.

Installs Ubuntu's own docker.io and compose packages, so there is no third-party apt source to audit. Caps each container log at 10 MB times three files, and adds the bootstrap user to the docker group. File: steps/60-docker.sh.

Verify

cat /etc/docker/daemon.json
docker info | grep -i 'logging driver'

Run docker info after logging in again, so the group change applies.

8 proxy Serving apps without TLS, and certificates you have to renew by hand.

Installs Caddy (default) or Nginx with certbot (BOOTSTRAP_PROXY), or nothing with none. With BOOTSTRAP_DOMAIN set it proxies to BOOTSTRAP_PROXY_UPSTREAM over HTTPS. Without a domain it writes a port 80 placeholder. File: steps/70-proxy.sh.

Verify

caddy validate --config /etc/caddy/Caddyfile
curl -I http://127.0.0.1

With Nginx use nginx -t. Certificate issuance needs a public DNS name and is not tested in CI.

9 monitoring Not noticing CPU, memory or disk pressure until the site is already down.

Optional, off unless ENABLE_MONITORING=1. Installs Ubuntu's prometheus-node-exporter on its localhost default. It opens no firewall port. File: steps/80-monitoring.sh.

Verify

curl -s http://127.0.0.1:9100/metrics | head
10 ssh Password guessing and root login over SSH. Runs last, because it can lock you out.

Writes a drop-in that turns off root login and password auth. It prints a lockout warning, refuses if the bootstrap user has no key, and needs BOOTSTRAP_CONFIRM_SSH=1 when not run interactively. It checks the file with sshd -t, restores the old one if that fails, then confirms the live settings with sshd -T. File: steps/90-ssh.sh.

Verify

sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication'
ssh deploy@your-server   # from a second terminal, before closing the first

Only the refusal and the dry-run warning are tested in the container. A live sshd reload and second-session login are not.

What works

  • works Dry run: prints each change it would make and writes nothing. A container test compares file checksums before and after.
  • works Re-run: the second real run in the test container exits 0 and reports "No changes were needed".
  • works --list, --only and --skip to select steps; refuses non-root real runs and anything but Ubuntu 24.04.
  • partial Tested in an ubuntu:24.04 container, not on a VPS. Swap, UFW enablement, service restarts and a live SSH reload are not exercised.
  • partial Nginx with certbot is written but certificate issuance is not tested; Caddy is the default path.
  • not done Ubuntu 22.04: the proxy step failed there because Caddy is not in its archive, so the script refuses it.

What this does NOT secure

This is a starting point for one Ubuntu VPS, not a security program. It does not:

  • Replace your provider's firewall, security groups or DDoS protection. UFW only filters on the host.
  • Protect against zero-days, a compromised apt package, or an image that was already bad when you booted it.
  • Set up intrusion detection, EDR, auditd rules, AppArmor policy or integrity monitoring.
  • Manage secrets, vaults, SSH certificate authorities or hardware keys.
  • Guarantee you cannot lock yourself out. The SSH step can cut off password and root login; prove key login in a second session first.
  • Secure your applications: no WAF, headers, database auth or image scanning. Docker and the proxy only prepare a place to run them.
  • Open or secure monitoring ports. The node exporter stays on localhost until you decide otherwise.
  • Give you compliance evidence for PCI, HIPAA or SOC 2.
  • Update itself. Pull a new release and re-run it.
  • Recover a broken server. Keep your provider's console access available.

The same list is in SECURITY.md, along with how to report a vulnerability privately.

Quickstart

Use a throwaway Ubuntu 24.04 server, with your provider's console available. Apply everything except SSH, prove key login from a second terminal, then harden SSH. 

git clone https://github.com/mohamedtaqysalmi/server-bootstrap
cd server-bootstrap
./bootstrap.sh --list
sudo ./bootstrap.sh --dry-run
sudo BOOTSTRAP_SSH_PUBKEY="$(cat ~/.ssh/id_ed25519.pub)" ./bootstrap.sh --skip ssh
# open a second terminal and log in as deploy with your key, then:
sudo BOOTSTRAP_CONFIRM_SSH=1 ./bootstrap.sh --only ssh
sudo ./bootstrap.sh   # second run: expect "No changes were needed"

How it works

bootstrap.sh loads the helpers in lib/, checks the OS and root, then sources each file in steps/ in name order. Every change goes through one counter, which is how a re-run can say it changed nothing. 

bootstrap.sh --dry-run | --only | --skip
   │
   ├─ check: Ubuntu 24.04? root? (dry run needs no root)
   │
   ├─ for each steps/NN-name.sh, in order:
   │     already as wanted?  ──► "ok" (nothing counted)
   │     otherwise           ──► "change" (counted)
   │                              dry run: print the command
   │                              real run: back up the file, then do it
   │
   └─ summary: "N change(s) made" or "No changes were needed"

How I built it

Plain bash, not Ansible

I wanted one dependency-free script that a reader can audit top to bottom on a fresh server before running it as root. Ansible would handle idempotency for me, but it is one more thing to install and trust. The cost is that I wrote the idempotency helpers myself and test them in a container.

SSH hardening runs last

Turning off password login before a key works is how people lock themselves out. The step refuses without a key, asks for confirmation, validates with sshd -t, restores the old file on failure, and checks sshd -T afterwards.

One wrapper for every change

Steps do not call mutating commands directly. They go through run, which prints instead of executing under --dry-run, and the file helpers back up before they overwrite. That keeps dry-run honest.

Caddy as the default proxy

Caddy gets and renews HTTPS certificates from a short Caddyfile, so the default path stays short enough to audit. Nginx with certbot is there for people who already use it.

Limits and roadmap

  • It has not been run on a real VPS yet. That is the next thing I want to do, and I will record the result in the test report.
  • One server, one run at a time. There is no inventory and no remote execution.
  • The Lighthouse scores in the test report are still pending.

Open work is in the issues. To change a step, start with CONTRIBUTING.md: every step has to be idempotent and support dry-run.
